Static Hermes explores optional sound typing and ahead-of-time JavaScript compilation in the Hermes static_h branch. Its published design describes Clang/LLVM generation for native code and WebAssembly, retaining an interpreter for dynamic code such as eval. Static Hermes’s native compilation explanation.

kiln packages an application workflow around TypeScript: source checking, immediate interpretation, native builds, a Node compatibility host and explicit concurrency tools. The useful comparison is which compiler and host combination can run your program and preserve the behavior it relies on.

TypeScript diagnostics are their own compatibility target.

Accepting annotations, making sound type guarantees and matching TypeScript diagnostics are separate goals. Static Hermes’s optional typing design should be evaluated on its own terms. For a TypeScript project, decide how authored source is checked and lowered before comparing the compiled program.

kiln includes kiln check, with TypeScript 7.0.2 library inputs and recorded exact and partial diagnostic matches. Compiler contracts can help guarded native specialization; unchecked annotations are not runtime proofs. TypeScript checker architecture and recorded differences.

Language semantics and host APIs both matter.

A standalone JavaScript engine and a Node application runtime solve different integration problems. For a file-processing CLI or HTTP service, check filesystem, networking, module resolution and lifecycle behavior in the actual host you plan to ship.

kiln supplies a Node adapter and native builds for those programs. Its conformance reference separates ECMAScript behavior, diagnostic fidelity and real package smoke tests. Typed actors, parallel collections and immutable graph sharing are additional application APIs. Conformance evidence · Built-in API reference.

Do not confuse Hermes bytecode with native AOT.

kiln’s existing real-world runner invokes hermesc -emit-binary to produce an HBC file and executes that file with hvm. Building those tools from static_h does not turn that execution into a native-AOT benchmark. That lane can inform bytecode comparisons, but it cannot establish a kiln-versus-Static-Hermes native speed ranking. Inspect the exact build and execution commands.

Which should you evaluate first?

Evaluate Static Hermes when your work centers on JavaScript engine integration, its typing approach or native/Wasm compiler research. Evaluate kiln when you want a TypeScript CLI or service workflow with package resolution, source diagnostics and built-in ownership APIs. Run the same program in the intended host before deciding.
