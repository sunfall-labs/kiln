## Notes on this baseline (hand-written)

- **Noise.** The machine was shared with other agents' builds throughout: the 1-minute load
  average before each job had a median of 20.5 and reached 39.9 on 16 hardware threads, and 91
  cells spread by more than 25% across rounds. Read every figure to one significant digit and
  compare columns within a row rather than across runs. A `--quick` run twenty minutes earlier at
  a load of 5-12 gave the same ordering everywhere, with smaller absolute times (for example
  node/bun worker start 22 / 9.8 ms, `KILN_WORKERS=1` process start 4.5 ms against bun 4.4 ms and
  node 23 ms; servers at all cores kiln 338k, bun 314k, Go 221k, node `cluster` 157k rps).
- **`parallelMap` does not help today, for two different reasons.** (a) The heavy callback (a
  loop) is not accepted by the typed pool, so it takes the sequential lowering: the default and
  `KILN_PARALLELISM=1` rows match, both slower than `map`. (b) The light callback, which the typed
  pool does accept, does not compile at `1e46b859`: the emitted pool guard in
  `crates/kiln-backend-c/src/emit_graph/ops/call_method.rs` (the `parallel_pool_intrinsic` block)
  names `kiln_inheriting_new_target`, which no longer exists (the register is
  `kiln_c99_inheriting_new_target`). Any `arr.parallelMap(x => <arithmetic>)` hits it, with or
  without `--node`. Side measurement, **not part of the table**: with that one identifier renamed
  in a scratch build, the light `parallelMap` answers the same checksum in ~19 ms against ~119 ms
  with `KILN_PARALLELISM=1` and ~56 ms for kiln's `map` (Go: 16.7 ms on goroutines).
- **A second emitter bug, worked around in the suite.** `for (let i = 0; i < 13; i += 1)
  cats.push({ code: i * 3 })` fails to compile natively (the integer-multiply fast path writes an
  undeclared double temporary `d<n>`). `js/common.mjs` writes `(i * 3) | 0` instead, which is the
  same value; the workaround is commented there.
- **kiln's in-realm `MessageChannel`** runs at thousands of messages per second (one-way ~8k/s,
  ping-pong ~150 µs) against node/bun's hundreds of thousands, and "transferring" a 16 MB buffer
  costs about as much as copying it -- the transfer list appears to copy. Worth an issue of its own
  before worker_threads (06) builds on the same port.
- **kiln at 100,000 tasks** needs 2.9 s and 732 MB peak for what bun does in 0.57 s / 196 MB and
  Go in 0.3 s / 208 MB; at 10 and 1,000 tasks every runtime sits on the 100 ms floor.
- **Server.** `oha` shares the cores with the server, so all-core rps is bounded by the load
  generator and by the other load on the box; kiln's `KILN_WORKERS=auto` led every round. kiln's
  tree PSS (172 MB for 17 processes, ~10 MB per realm process after load) is the number the thread
  mode (07) and the shared region (08) should shrink.
