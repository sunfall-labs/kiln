## Notes on this baseline (by hand)

- **Noise.** Load was 7-21 on 16 hardware threads, other agents' builds alongside. That is why
  nearly every cell is `~`. The all-core columns suffer most, because they compete with the builds
  for the same cores. Read the ratios, not the milliseconds. "(dirty)" is this suite's own
  uncommitted `bench/harness.mjs` `checksum` hook, which is part of this commit.
- **kiln's sequential typed-array methods are the outlier, not the pool.** `map`/`filter`/`reduce`
  on a `Float64Array` cost 400-560 ms per million elements in kiln, against about 20-60 in node.
  Its default typed `sort` costs 5.3 s. These are the TypeScript built-ins, which make a generic
  call per element. So "vs kiln seq" is flattering, and `@1` against node is the fair single-core
  comparison: the typed pooled worker on one thread beats node's method on every numeric row
  except `sort-typed` (79 against 116 ms here). `Float64Array.prototype.slice` costs ~200 ms per
  million elements, which is why `sort-typed` copies with `new Float64Array(xs)`.
- **`pipeline-objects` is slower parallel than sequential (0.9x; `@1` 137 against 101 ms).** The
  array that `records.map(...)` returns makes the pooled `parallelFilter`/`parallelReduce` decline
  at run time. Their time does not change with the thread count, so the TypeScript sequential
  definition runs instead. Measured in isolation, 1M elements: `parallelFilter` 37 ms against
  `filter` 7.8, and `parallelReduce` 137 ms against `reduce` 2.3. The same values pushed in a loop
  run pooled and fast. Repro: `const xs = recs.map(r => r.p * 2)` over an array of
  `{ p: (i % 1000) + 0.5 }`, then `xs.parallelReduce((a, v) => a + v, (a, b) => a + b, 0)` against
  `xs.reduce((a, v) => a + v, 0)`: 138 against 2.4 ms at 400k, 460 against 14 at 1M. This breaks
  the PRD's "never slower than `map`".
- **`pipeline-records` in kiln** is dominated by its sequential first stage (tier 2). kiln's
  `parallelMap` fallback is about 30x faster than its own `map` on the same callback, because
  typed `map` is the slow built-in above.
- The pool and Go rows fuse each pipeline into one loop. That, not the thread count, is most of
  their lead on the pipeline rows (see README).
