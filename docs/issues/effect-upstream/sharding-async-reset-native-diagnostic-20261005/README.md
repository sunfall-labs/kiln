# Sharding async-reset native diagnostic

This is a one-case-at-a-time diagnostic overlay for the pinned Effect Sharding tests. It is not a full-suite result and does not change the upstream test bodies or their default 5-second deadline. The original workspace at `~/.cache/kiln/effect-final-322-20261004` and the final 322-case workspace were left untouched. Private full copies of the pinned `source/` and `node_modules/` trees were used because the production resolver correctly rejected an external symlink into the original `node_modules`; the first failed build log is retained. The dependency packages `effect`, `@effect/vitest`, and `@effect/opentelemetry` were redirected to the local overlay copies. Production project-root checks were not changed.

The original 66 registered Sharding case IDs were compared in exact order against the frozen profile inventory. The selector then retained one selected test and its ancestor suites, before hook traversal. The private `Sharding.ts` source emits only numeric counters and a numeric source marker; it does not retain messages, fibers, scopes, contexts, or clock objects. Clock identity is represented through a `WeakMap`, and the instrumentation records already-read time/deadline values rather than asking the clock again. Marker `1942908154` confirms the private instrumentation was loaded; the pristine Bun controls have no counter instrumentation. Both overlays retain copied source inputs and local dependency aliases. The test callback and assertions are copied byte-for-byte from the pinned source.

Bun 1.4.2 passed both selected cases in both the instrumented and pristine overlays. On the single frozen native-release binary, the passing remote-reset control completed after 10 storage reads. The asynchronous-reset case still failed at the unchanged 5-second case deadline, after 26 storage reads. In that failed case the counters show exactly one persisted/local outgoing request, one reset ID claim and one reset call, with no retry or remote-send churn. The Bun instrumented copy passed the same async-reset test after 127 storage reads. The evidence therefore narrows the gap to native progress/throughput during the async storage-reset path. It does not yet identify the operation responsible for the slower progress, so no retry or runtime optimization is inferred.

The native build used CLI `16958abcd29f328d23bb789fc188f0e55a065e349b0b77736ce0354ba1820ceb` (`native-release`, symbols retained), provider ABI 82, archive `61c1ef04a85b93ec98e561e320d4c056f6c2a07e788a25f71f1273f4ef5c2f6d`, and had `KILN_NATIVE_GC_STRESS` unset. The resulting 290,657,192-byte executable SHA-256 is `e3db1b40fd1ff66014e715d741dbb3b4f3e20a9dc2e75b4c865edac6695faad5`. The exact full CLI, manifest, archive, source, binary, and log hashes are in `native-counterprobe-receipt.json`; the exact command and resource constraints are in `native-build-plan.json`. Full logs for all selected Bun and native invocations are in `logs/`. Bun's post-summary “directory mismatch” message is retained; Bun exits 0 on those runs.

The source snapshots here are for reproducibility: `source/Sharding.test.ts` is the unchanged pinned test; `source/Sharding.pristine.ts` is the unchanged pinned implementation; `source/Sharding.instrumented.ts` is the private counter-only instrumented copy. Their checksums and the copied harness/setup inputs are in the receipts. The native executable and provider archive remain in the owned scratch overlay rather than being committed due to their size.
