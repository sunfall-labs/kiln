# Sharding async-reset clock progress diagnostic

This follow-up adds numeric-only hooks to the private `TestClock.ts` overlay. The original Sharding test, assertions, and 5,000 ms harness deadline remain unchanged. Hooks record only values already read by `run`: call count, start/end timestamps, fired sleep timestamps and queue length, and started/completed `yieldNow` counts. No additional clock reads or retained runtime objects are involved. Instrumented TestClock source SHA-256: `a9711ffcc3b9fd71351b8a8880f08a7489e8cc0f10c8c4195711b54a0ab30db3`; the existing instrumented Sharding source SHA-256 remains `ae9a9d16c3cbef70d224c07434936249d549d7cebb28c8bfdbc8ffe8348702d3`.

The default native-release binary used CLI `16958abcd29f328d23bb789fc188f0e55a065e349b0b77736ce0354ba1820ceb` and ABI-82 provider manifest `b03c48a204de3f911b424ce62b7d96a88ef595de0f99217cba8c34caf6c5dd6e`. The diagnostic executable SHA-256 is `ab63f16401c2159dc2011d7a19f8c8a441a4fb1889f6de3927622f4d820d7343`. Under concurrent build load, async-reset still timed out: four clock runs requested start `5002` ms and end `605002` ms, but only 152 sleeps fired (151 yields completed), with the last fired timestamp at `99000` ms. The remote-reset control passed and matched Bun exactly: six runs, start `5004` ms/end `10004` ms, 17 sleep yields completed, and ten storage reads. Bun's async-reset passed the same 605002 ms advance with 939 sleeps fired/completed and 127 storage reads. These observations show the test clock target agrees across runtimes, while native processes substantially fewer wake/yield steps in the fixed real-time budget. They are attribution under shared load, not a quiet timing result.

A separate private build set `KILN_GENERIC_OPT=1`, which the compiler includes in generic-module compile identity and which compiles generic-only modules at `-O1` instead of the default `-O0`. The build used the same frozen CLI/provider, one worker, an 8 GiB address-space cap, and the unchanged native-release profile. It took 26m 03s: 95,010 ms emission, 1,464,098 ms compilation, 390 ms link; output executable SHA-256 `464e2efc22305a7bdf2d02f470848042692881f56d3c584666765cdaf6fb5cbd`. The selected async-reset case still timed out. One run reached 193 yields; the measured repeat reached 177, compared with 152 on the default binary. A remote-reset control continued to match at 17 yields. Do not promote this compile override: it changes codegen and cache identity, had a long compile, and the incomplete improvement was measured under concurrent load.

Per-process child CPU accounting for the selected async-reset test found the default native run used 5.037 s user CPU and 0.204 s system CPU in 5.405 s wall time; the generic-opt run used 4.974 s user and 0.165 s system in 5.177 s wall time. Instrumented Bun used 1.511 s user plus 0.318 s system CPU in 1.068 s wall time. This indicates the native run was CPU-saturated rather than parked on a long OS wait. The measurements are bounded-load diagnostics, not quiet performance claims.

The retained earlier 500 Hz profile has 2,399 native samples over about 5.26 s. Inclusive samples include `drive_one_ready_turn` (593, 24.7%), `kiln_c99_run_timer` (589, 24.6%), and `run_one_timer` (587, 24.5%); nearly all `run_timer` samples descend through `run_one_timer` into `kiln_c99_call_inner`. Top leaves include method dispatch, key hashing, property reads, and Sharding's `sendOutgoing`. The profile predates the TestClock hooks and overlaps full-suite compilation, so it localizes CPU activity to callback/ready-turn work but does not prove a specific causal hot function.

A no-build `KILN_GC_TRACE=1` replay of the default frozen binary also timed out at the unchanged deadline. It performed 188 collections and reclaimed 4,512,094 blocks / 653,992,549 bytes in total (median 3,445,725 bytes reclaimed per collection; live bytes ranged from 2,331,172 to 12,524,470). The child used 5.017 s user CPU, 0.191 s system CPU, and 5.329 s wall time, with a 180,776 KiB maximum RSS. This confirms substantial allocation and collection activity during the timeout, but the existing trace reports only collection totals: it does not time GC or attribute allocations to a call site. The run advanced 143 sleep callbacks / 142 yields and 24 storage reads, so tracing slightly changed progress and these counts are not directly comparable to the uninstrumented run. It still ended in the same timeout.

The native runtime has no existing environment switch for per-yield or per-call counts. `KILN_HEAP_PROFILE` emits heap snapshots at introspection checkpoints, not call-site attribution. Together with the earlier sampled stack (`run_one_timer` into `kiln_c99_call_inner`) and CPU accounting, the evidence points to CPU work in ready callbacks; GC volume may contribute, but the current data does not establish it as the cause. Do not infer a GC optimization from this trace.
