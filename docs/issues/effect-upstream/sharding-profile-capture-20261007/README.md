# Sharding native profile capture (2026-10-07)

This is a diagnostic profile of the unchanged 66-case Sharding native corpus, not an acceptance or performance comparison. The original per-case 5-second deadlines and test sources were unchanged. All three captures used the same retained native binary: SHA-256 `9c52f066f47dbe62b94dd321e15f403ef39bf6bca5c1a05fe04c241842002135`, 222,096,616 bytes; ELF Build ID `47b3e91c3dc1884b9f2d143a6b05f940a81bb530`. The profile library code ID and `readelf -n` Build ID match. Its CLI SHA is `af80860eda702b4d6d6742ca15e5b23013fe65649e759b0078aba1ffdef73d27`, compiler source commit `c06c78329eb9c30f2c8ab44007b5054bb4a1dc2b`.

The direct-launch attempt is rejected for attribution: it produced only 15 samples, 127 ms of thread CPU, and no library records. The first attached capture is also insufficient for hotspot conclusions: 171 samples over 18.886 seconds and 1.688 seconds of thread CPU, with 16 gaps above 100 ms and a 3.723-second maximum gap. Its sampler exited successfully, but the retained data do not identify why so much CPU was uncaptured. Both earlier captures still record the exact same 61 passes and five timeout failures; they are retained only as limited evidence.

The improved capture starts sampling after the inventory line and verifies `/proc/<pid>/exe` against the retained binary. It records paired Unix and monotonic nanoseconds at launch, sampler attach, every output line, each case result, and process end. It also records `/proc/<pid>/stat` every 100 ms and at each case marker, then records `RUSAGE_CHILDREN` immediately after the native child exits and before waiting for the sampler. Samply ran at 100 Hz without unstable presymbolication. `KILN_NATIVE_GC_STRESS` was unset. The run exited 1 with 61/66 cases, the same five original timeouts; wall time was 48.361 seconds, and child usage was 44.225 user + 1.133 system seconds.

This capture contains 4,531 samples spanning 47.922 seconds and 45.189 seconds of thread CPU, 99.6% of the child CPU usage. The first sample followed attach by 0.364 seconds; the final sample was about 11 ms before child exit. Sample monotonic timestamps align to the recorded case-result marker intervals. Those intervals include harness and cleanup work around each test body, so they are approximate test windows rather than exact callback boundaries. Across the five failing windows, the profile accounts for 24.698 seconds of CPU versus 24.97 seconds from per-marker process-stat ticks (98.9%); passing windows account for 20.480 versus 20.37 seconds (100.5%, rounding and boundary effects).

PCs were symbolized offline only when the address fell inside exactly one symbol range from `nm -n -S --defined-only` on the binary whose Build ID matched the profile. Ambiguous or unresolved addresses were left unresolved. The captured failing-window leaf CPU is distributed across `kiln_c99_gc_lookup_nursery` (0.754 s), `kiln_c99_get_own_kind` (0.717 s), `kiln_val_to_boundary` (0.690 s), `kiln_c99_invoke_method_dispatch` (0.678 s), `d26041571cf61f0bad70365407312980_fn_77` (0.534 s), `kiln_c99_intern_key` (0.508 s), `kiln_c99_property_read_own_with_hash` (0.502 s), and `kiln_c99_key_hash` (0.491 s). No single leaf dominates. Inclusive stacks repeatedly contain `9f9747a19882905c65626196c02048b1_fn_50` (24.259 s sampled across these windows), `_fn_48` (24.239 s), and timer/ready-turn frames (`kiln_c99_run_timer` 23.735 s; provider `drive_one_ready_turn` 23.695 s). These are overlapping inclusive totals: they show the recurring loop/callback path, not the unique cost of a kernel. Passing windows have a similar generic leaf mix. This evidence supports CPU-bound execution, but does not justify a specific runtime optimization by itself.

The `raw/profile-captures.tar.zst` archive contains the complete direct-launch, sparse-attachment, and improved-attachment output directories, including raw profile files, full native logs, marker arrivals, process snapshots, sampler commands/logs, and terminal receipts. The large native executable is not included; its SHA-256 and Build ID are recorded above. `SHA256SUMS` covers the archive and this report.
