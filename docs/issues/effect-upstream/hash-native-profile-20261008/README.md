# Hash native baseline profile and O2 experiment

This archive records a fresh CPU profile of the original-deadline Hash native run and the selected-function O2 experiment. The baseline and O2 runner reports each contain all 25 original Hash cases: 24 passed, the same one timed out at its unchanged 5,000 ms budget, and none were skipped. This is diagnostic evidence, not a full Effect-suite result or a quiet performance comparison.

The retained baseline executable has SHA-256 `39077c4caff561edef0425d1fe43f978c34eef2bdffc2d041e6cbb95225d0067`, built by CLI `1d0c39f6f15188edd9850fdacbbe5e09a58634d27920f5f7bc112b4e498a20d7`. Its only failed case was `Hash > hash law > hashes a HashMap like a fresh build after persistent and in-place edits`, with `TEST_TIMEOUT: 5000ms`. The O2-selected-functions candidate is source commit `3c50fdc3`; its CLI is `f42c1190ec762ad33aa061653387e972316673fffb477c0c838728be248415a0` and its executable SHA-256 is `eb7dd46b35f217af57dcb8467447f64753c7fe11a7ea7749d31bcbcdc5a326b9`. It retained the same 24/1/0 outcome and same timeout. The O2 experiment therefore did not clear the case; its runner wall times must not be interpreted as a performance result.

The profile sampled the baseline executable at 100 Hz. It contains 1,868 samples in the native thread; 1,207 fall in the marker interval ending at the failed case. That interval spans 21.267 wall seconds while sampled, includes setup/cleanup and possible async spillover, and is not the original acceptance timing. Counts below are sample observations, not time fractions or exclusive costs.

The largest requested leaf counts in that interval were:

| Runtime helper | Samples attributed to helper | Source-qualified caller evidence |
| --- | ---: | --- |
| `kiln_val_to_boundary` | 45 | Mostly method dispatch from HashMap `fromIterable` (fn69), `IndexedNode.remove` (fn59), plus harness and other HashMap functions. |
| `kiln_c99_new_object_sized` | 43 | 25 caller-group samples reach HashMap fn59 via `kiln_c99_invoke_method_dispatch`; 17 reach fn69; additional stacks include Equal comparison, HashMap fn38, and `kiln_c99_build_arguments_object`. |
| `kiln_c99_gc_lookup_nursery` | 41 | Marking/owner-root paths and weak-key liveness/pruning, reached while allocation-triggered collection runs in fn59/fn69 and the harness. |
| `kiln_c99_gc_trace` | 39 | Collector drain/object-property/root tracing, with nearest Effect frames fn69, fn59 and fn38. |
| `kiln_c99_own_index_key_with_hash` | 34 | Own-property lookup and dictionary-index probes, including HashMap fn20 and fn69; other observations include private/member lookup and harness setup. |
| `kiln_c99_gc_finalize` | 34 | Nursery settlement during collection, reached in fn59/fn69 and Equal's `equals` (fn1). |

These stacks support a broad cost picture: persistent HashMap node construction/removal and collection both appear in the failed interval. They include actual object construction through constructors and `kiln_c99_new_object_sized`, including HashMap node work; they are not all call-context adapters. Some samples separately show arguments-object allocation in Equal's `equals`, so the profile does not justify assigning every allocation to HashMap nodes. `kiln_c99_gc_lookup_nursery` is reached from marking and weak-key liveness paths; it is not evidence by itself that nursery lookup dominates collection.

`kiln_val_to_boundary` is the internal runtime bridge from compact `kiln_val` to tagged `kiln_value`. Its source in `runtime/boxed.c` branches on number/special tags, and for general object-like pointers may call `kiln_c99_gc_kind_of_ptr` to recover the boundary tag. `kiln_val_from_boundary` reverses tags and canonicalizes numeric NaNs. This is an internal outlined-runtime/value representation seam, not a provider-ABI crossing on every operation. The sampled method-dispatch paths show where conversions are encountered; they do not establish that every operation converts compact → boundary → compact, nor that numeric conversion is the expensive part. Method dispatch takes `kiln_value` receiver/argument/result values in `dispatch_part_a.c`.

The observed nursery lookup is a bounded membership check: `kiln_c99_nursery_locate` checks the nursery address range and current bump region, then masks to a region and probes the region set; `kiln_c99_nursery_block_at` checks the allocation bitmap. The sampled frames are consistent with collection work being interleaved with persistent node allocation, but they do not show that the lookup itself is a linear scan or the dominant cost. Likewise, `kiln_c99_own_index_key_with_hash` consults an optional dictionary hash index when present and otherwise falls back to ordered property comparison; its sample count alone does not show which path or how many probes each read used.

The function mappings are tied to the exact generated-C cache payloads and pinned source digests in `profile-receipt.json`: HashMap module fn52 is `IndexedNode.set` (source lines 519–546), fn59 is `IndexedNode.remove` (565–580), and fn69 is `fromIterable`. Equal module fn1–5 are `equals`, `compareBoth`, `compareObjects`, `compareOnPath`, and `compareStructure`. The exact source file is `source/packages/effect/src/internal/hashMap.ts`, SHA-256 `1a57c3acbbb04d14fec2ef6221dab4a2d0567dd66646476ddc293bb8f537cfc3`; the Equal source digest is also recorded in the receipt. These are caller mappings, not claims that those functions exclusively own the sample cost.

## Contents and verification

`profile.json.gz` and `profile-symbols.json` retain the raw sampled profile and its symbol sidecar. `profile-attribution.json`, `profile-caller-attribution.json`, and `profile-caller-summary.json` retain the helper/stack analysis; the summary omits the caller analyzer's placeholder `inclusive_sample` field and preserves its attributed sample and caller-group counts. `profile-analysis.py` and `profile-caller-attribution.py` are the analysis scripts. Baseline/O2 runner reports, native logs, and build logs are included. `SHA256SUMS.json` lists every archived file except itself. The full binary and large toolchain are not copied into this docs archive; their hashes and provider/source/CLI identities remain in the reports and profile receipt.

The baseline profile's symbolized relink reused every application, prelude, runtime, and launcher object; it compiled zero objects. The baseline executable and symbolized relink had identical `.text` address, size, and SHA-256 (`8775d2d1f581032474bc70c3966c6765d396dba0da17a1532eeee8328dceaf11`). The relink thus supports local symbol attribution without changing compiled machine code. The preserved first profiler attempt is excluded because its child was not executable and exited before running.
