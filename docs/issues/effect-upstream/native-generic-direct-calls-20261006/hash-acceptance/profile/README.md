# Hash timeout-window profile

This is a diagnostic profile of the unchanged native `Hash` acceptance run in the parent directory. It keeps the original 5,000 ms per-case deadline. The failing case is `Hash > hash law > hashes a HashMap like a fresh build after persistent and in-place edits`; it remains the same 24/25 outcome from the acceptance replay.

The timestamped interval from the previous case marker to the failing case marker is 5.649773 s wall time. It contains 1,318 samples for the native thread. The profile's thread CPU deltas sum to 5.288408 s over that window, so this case is CPU-bound on approximately one core. The interval includes harness setup, cleanup and any preceding asynchronous activity; it does not isolate only the test callback.

The largest self-sample symbol is `kiln_c99_gc_trace` at 52/1,318 samples (3.95%). Other leading self samples are `kiln_c99_new_object_sized` (3.49%), `kiln_c99_key_hash` (2.96%), `kiln_val_to_boundary` (2.88%), `kiln_c99_invoke_method_dispatch` (2.73%), `kiln_c99_get_own_kind` (2.43%), `kiln_c99_gc_lookup_nursery` (2.35%) and `kiln_c99_intern_key` (2.12%). No single self symbol accounts for even four percent of the window.

Module-qualified inclusive stacks repeatedly include the pinned Effect implementations: `Equal.ts`'s `compareBoth` and `compareObjects` functions each occur in roughly 41% of samples, while `internal/hashMap.ts` function 59 occurs in 32.0% and function 69 in 29.5%. The generated C metadata identifies function 69 as `fromIterable`; function 59's frontend byte span lands in `IndexedNode.remove`. Function 52's span lands in `IndexedNode.set` (1.2% self samples). These paths fit the upstream workload, which performs up to 40 persistent or mutable edits per iteration, builds a fresh map with `fromIterable(Array.from(map))`, and compares both equality and hashes for 100 iterations. This is attribution, not proof that a particular source operation alone causes the timeout.

Inclusive counts for `kiln_c99_construct_with_new_target`, `kiln_c99_call_inner`, and other call wrappers are high because they enclose much of the test's execution; they are not self-cost estimates. The profile therefore does not justify a single-function patch. It points to broad repeated work across HAMT edits/rebuilds, structural equality, native calls, allocation, key processing and GC. A useful next experiment should measure operation counts or scaling across map sizes/iteration counts under a diagnostic copy, while keeping the committed upstream assertions and deadline unchanged.

## Identity and limitations

The profiled executable is the retained-symbol AOT image with SHA-256 `27243ee61cfd074dc63c23f61b375e2f2264565392e43575535cfc7b08ac77a4`. It reproduces the full 25-case outcome (24 pass, the same timeout). The exact target PID's `/proc/<pid>/exe` digest was checked during the profile. The profile uses the same CLI source (`6d5fe097bc9bb81816f6b845a495b846dc724883`), pinned Effect source (`67ba4e46a11ccda0b6761578bfd22c04ae00167d`), and provider recorded in the parent receipt.

This image was relinked with symbols. Its `.text` digest differs from the original stripped acceptance binary, so these symbol offsets are interpreted only against this symbolized image; they are not mapped onto the stripped binary. The build log shows generated C and every application/runtime object were cache hits (emission 9.08 s, compilation 0 s, link 0.256 s). The timestamp-window monitor first observed the Python supervisor executable before it exec'd the native target; the profile itself names the native target thread, and the direct full-run symbol profile separately verified the target executable SHA. The monitor startup race is retained in the receipt rather than hidden.

`analyze.py` derives the case window from the timestamped marker log and symbols from the retained Samply sidecar. `analysis.json`, the compressed profile, symbol sidecars, timestamped output, monitor receipt and symbol relink log are retained here. No binary is included in this evidence directory.
